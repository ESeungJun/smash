# smash 개선안

점검일 2026-11-10 · 대상 커밋 `f56dbed` (v2.2.0)

## 한 줄 정의

다운로드·문서 폴더가 쌓이는 사람이 한 번 정해 둔 규칙으로 파일을 분류 폴더에 옮기고, 누르는 순간 화면에 손바닥이 "찰싹!!" 내려오는 Mac·Windows 정리 앱. 로그인된 Claude(CLI·MCP)가 규칙 밖 파일과 규칙 작성을 거든다.

## 컨셉·의도

- "방 좀 치워라!" 엄마의 등짝 스매시(`README.ko.md:22-23`). 정리 앱은 많으니 한 번 더 누르고 싶게 만드는 것이 목표다(`docs/결정기록.md:98`).
- 재미보다 안전이 먼저라는 결정이 기록돼 있다. "정리 앱은 파일을 한 번 날려 먹으면 다시 안 쓴다. 미리보기·휴지통·되돌리기부터 단단하게"(`docs/결정기록.md:53`). 이 문서의 점검도 그 기준으로 봤다.
- 대상: 규칙을 직접 만드는 개인 사용자. 한글 파일 이름(NFD)과 용도 낱말(영수증·계약서·카카오톡)을 다루는 점에서 한국어 사용자가 1순위다.
- 배포: GitHub 릴리스. 맥은 유니버설 dmg(Developer ID 서명 + 공증), 윈도우는 서명 없는 NSIS 설치 파일. Tauri updater 로 자동 업데이트. 무료, MIT.
- Claude 연동은 API 키 없이 사용자 PC 의 `claude` CLI(도구 끔)와 stdio MCP 서버(`smash --mcp`)로 한다.

## 구조와 스택

- `src-tauri/src/`(Rust, 약 5,000줄): `organizer.rs` 스캔·계획·실행·기록, `watcher.rs` 자동 정리, `config.rs` 설정·경로, `grouping.rs` 소분류, `trash.rs` OS 휴지통, `claude.rs` CLI 호출·MCP 등록, `mcp.rs` stdio JSON-RPC, `thumbs.rs` 썸네일, `lib.rs` 창·트레이·효과·명령.
- `src/renderer/`: 프레임워크 없는 HTML·CSS·JS. `app.js` 1,488줄(71KB)이 화면 전부. `tauri-bridge.js` 가 `window.tidy` 로 명령을 넘긴다. 빌드 단계 없이 `scripts/build-web.js` 가 `dist-web/` 로 복사만 한다.
- 데이터 흐름: 화면 `scan` → `scan_target` 이 `Item` 목록 → 화면이 체크된 항목을 `apply` 로 되돌려 보냄 → `apply_plan` 이 항목마다 다시 검증·이동 → `history.json` 에 `Run` 추가.
- 저장: `~/Library/Application Support/Smash/config.json`, `history.json`. 앱·자동 정리 스레드·MCP 프로세스가 같은 파일을 쓴다. 잠금 없음.
- 외부 의존: Tauri 2 + 플러그인 6개, `notify`, `sha2`, `chrono`. 휴지통은 `osascript`(맥)·`powershell`(윈도우)를 파일마다 실행.
- 권한: capability 는 `core:default` 뿐이고 파일·셸은 Rust 쪽에서만 한다. CSP 는 `default-src 'self'`.
- CI: `build.yml`(테스트 + 서명 없는 설치 파일), `release.yml`(태그 → 서명·공증 → 초안 릴리스 + `latest.json`).

빌드가 만든 `src-tauri/target`(3.8GB), `dist-web`, `src-tauri/gen`, `src-tauri/Cargo.lock` 은 점검 뒤 지워 저장소를 원래 상태로 돌려놨다.

테스트는 규칙 엔진의 순수 함수(`match_rule`, `glob_match`, `split_name`, `clean_folder`, `subfolders`, `normalize`, `clean`·`resolve`)와 통합 흐름(스캔 → 실행 → 되돌리기, 덮어쓰지 않기, 밖 거부)을 덮는다. 빠진 곳은 아래 문제마다 적었다.

덮어쓰기 경로부터 말하면, 계획과 실행 양쪽에서 `plan_move` 가 목적지 존재를 확인하고 디스크 간 복사는 `create_new` 로 연다. 정상 흐름에서 기존 파일을 덮어쓰는 경로는 찾지 못했다. 🔴 는 없다. 남은 위험은 되돌릴 수 없게 되는 경로들이다.

### 🟠 1. 정리 도중 앱이 끝나면 옮긴 기록이 남지 않는다

- **지금 문제**: `apply_plan` 은 모든 항목을 처리한 뒤에야 `history.json` 을 한 번 쓴다(`organizer.rs:758-766`). 그 전에 앱이 종료되거나 전원이 나가면 이미 옮긴 파일의 기록이 없어 되돌릴 수 없다. 릴리스 빌드는 `panic = "abort"`(`Cargo.toml:46`)라 패닉 하나로도 그렇게 된다. 대상이 최대 20,000개이고 중복 검사에 해시를 읽으므로 실행이 길어질 수 있다. 기록 저장 실패도 `let _ =` 로 버린다(`organizer.rs:701`).
- **고치는 방법**: 실행 시작 때 `history/<runId>.jsonl` 을 열고 항목 하나를 옮길 때마다 `Op` 한 줄을 붙인다. 끝나면 `history.json` 에 합치고 지운다. 앱 시작 때 남은 `.jsonl` 이 있으면 "중단된 정리"로 기록에 넣는다. 저장 실패는 결과에 담아 화면에 알린다.
- **나아지는 점**: 어느 시점에 끊겨도 옮긴 만큼은 되돌릴 수 있다.
- **예상 결과**: 중단된 실행이 기록 탭에 "중단됨 · 옮김 312"로 남고 되돌리기가 된다. 테스트: 실행 중간에 강제로 끊고 되돌리기.

### 🟠 2. 되돌리기가 "마지막 정리"를 온전히 되돌리지 못한다

- **지금 문제** (네 가지가 겹친다):
  1. 일부가 실패해도 `undone = true` 로 닫는다(`organizer.rs:800`). 원래 자리에 같은 이름 파일이 있어 실패한 것(`:790-792`)은 다시 시도할 수 없다.
  2. 휴지통으로 보낸 파일은 목록만 돌려준다(`:802`). 맥에서 `trashItemAtURL` 의 결과 경로를 `null` 로 버려서(`trash.rs:15-16`) 휴지통 안 위치를 모른다. 중복으로 판단해 버린 파일도 여기 든다.
  3. "지금 전부 정리하기"는 폴더마다 `apply_plan` 을 불러 기록이 폴더 수만큼 생긴다(`lib.rs:436-449`). 화면에는 "마지막 작업 되돌리기" 하나뿐이라(`index.html:62`) 한 번 누르면 마지막 폴더만 돌아온다.
  4. 수동 정리 뒤에 자동 정리가 한 번 돌면, 되돌리기는 자동 정리 쪽을 되돌린다(`:776` 은 가장 최근 기록을 고른다).
  되돌린 뒤 새로 만든 빈 폴더도 남는다.
- **고치는 방법**: (1) 실패한 `Op` 만 남기고 성공한 것은 지운 뒤, 남은 것이 있으면 `undone` 을 닫지 않는다. (2) 맥은 JXA 에서 결과 URL 을 받아 `Op.to` 에 저장하고, 되돌릴 때 그 경로에서 원래 자리로 옮긴다. 윈도우는 1단계로 "휴지통 열기" 버튼. (3) `undo_run(id)` 를 추가하고 기록 탭의 각 줄에 되돌리기 버튼. `tidy_all_now` 는 `Run` 하나로 묶어 저장한다. (4) 되돌린 뒤 이 실행이 만든 폴더 중 빈 것은 지운다(`missing_dirs` 로 실행 전에 기록).
- **나아지는 점**: README 의 한 줄이 모든 진입점에서 사실이 된다.
- **예상 결과**: 기록 탭에서 어느 실행이든 골라 되돌리고, 휴지통 간 파일도 맥에서는 같이 돌아온다. 테스트: 실패 섞인 되돌리기 재시도, 두 폴더 묶음 되돌리기, 휴지통 복원(CI 한정).

### 🟠 3. 기록·설정 파일을 세 주체가 잠금 없이 쓴다

- **지금 문제**: `apply_plan` 과 `undo_last` 는 `history.json` 을 읽고 고쳐 통째로 쓴다(`organizer.rs:762-764`, `775-803`). 쓰는 쪽이 셋이다: 앱의 정리(`SmashQueue` 로 서로만 직렬화, `lib.rs:413-414`), 자동 정리 스레드(`watcher.rs:159`, 큐 밖), 별도 프로세스인 MCP 서버(`mcp.rs:189`). 둘이 겹치면 한쪽 기록이 사라지고 그 실행은 되돌릴 수 없다. `load_history` 는 파일이 깨져 있으면 빈 목록을 돌려주므로(`organizer.rs:691-696`) 다음 저장이 기존 기록 전부를 덮는다. 설정도 같다. 화면은 `state.config` 를 통째로 저장하는데(`app.js:72-74`) MCP 의 `add_rule` 이 그 사이 넣은 규칙을 모른다(`config:changed` 는 트레이만 보낸다, `lib.rs:618`).
- **고치는 방법**: 기록은 1번의 실행별 파일로 바꾸면 겹쳐 쓸 일이 없어진다(목록은 디렉터리 읽기). 설정은 저장 직전에 디스크의 수정 시각을 비교해 바뀌었으면 다시 읽어 합치고, 앱은 `config.json` 을 `notify` 로 지켜봐 `config:changed` 를 낸다. 깨진 `history.json` 은 `history.broken-<시각>.json` 으로 옮기고 새로 시작한다.
- **나아지는 점**: Claude 로 정리하는 동안 앱의 자동 정리가 돌아도 기록이 남는다.
- **예상 결과**: 동시 실행 테스트(스레드 둘이 `apply_plan`)에서 기록 2건이 모두 남는다.

### 🟠 4. 정리 대상 밖을 가리키는 규칙이 미리보기에는 나오고 실행에서 전부 실패한다

- **지금 문제**: `scan_target` 은 규칙 목적지가 정리 대상 안인지 확인하지 않는다(`organizer.rs:498-501`, `547`). `apply_plan` 은 확인한다(`:737-739`). 규칙 편집기는 아무 폴더나 고를 수 있고(`app.js:924`) 경고가 없다(`app.js:604-609`). 그래서 "PDF → ~/Archive" 규칙은 미리보기에 정상 이동으로 나오고, 누르면 손바닥이 내려온 뒤 "목적지가 정리 대상 폴더 밖입니다"가 파일 수만큼 실패한다. 화면에는 첫 번째 실패만 나온다(`app.js:466`).
- **고치는 방법**: `scan_target` 에서 밖을 가리키는 항목에 `note: "outside"` 를 달아 미리보기에서 체크 해제 + 사유 표시. 규칙 편집기의 `destPreviewHtml` 에 "정리할 폴더에 없는 곳이에요. [폴더로 추가]" 버튼. 추가하면 규칙 없는 대상으로 들어간다.
- **나아지는 점**: 미리보기가 약속한 것과 실행 결과가 같아진다.
- **예상 결과**: 밖 목적지 규칙은 저장 시점에 안내가 뜨고, 실행 실패 0건.

### 🟠 5. "N일 지난"이 수정 시각 기준이라 방금 받은 파일도 휴지통에 갈 수 있다

- **지금 문제**: `match_rule` 은 `mtime` 만 본다(`organizer.rs:250`). 압축을 풀거나 AirDrop·USB·`cp -p` 로 들어온 파일은 원래 수정 시각을 그대로 갖는다. 기본 규칙이 "7일 지난 설치 파일 → 휴지통"이고(`config.rs:296`) 자동 정리도 휴지통 규칙을 그대로 실행한다(`watcher.rs:121`, `159`). 오늘 받은 2019년 날짜의 `.pkg` 는 다음 정리 때 바로 휴지통으로 간다. 휴지통이라 복구는 되지만 🟠 2 때문에 되돌리기로는 안 돌아온다.
- **고치는 방법**: 기준을 `max(수정 시각, 폴더에 들어온 시각)`으로 바꾼다. 맥은 `getattrlist` 의 `ATTR_CMN_ADDEDTIME`(Finder 의 "추가된 날짜"), 윈도우·기타는 생성 시각. `FileInfo` 에 `added_ms` 를 더하고 `match_rule` 이 둘 중 늦은 값을 쓴다.
- **나아지는 점**: "받은 지 7일"이라는 사용자의 이해와 동작이 같아진다.
- **예상 결과**: 테스트 `old_mtime_new_arrival_is_kept` 추가. 이 맥의 다운로드 폴더에는 해당 파일이 지금 없었다(4개 중 0개).

### 🟡 6. 자동 정리가 "다 받아진 파일"을 잘못 볼 수 있는 경우

- **지금 문제**: 판정은 "수정 후 `autoDelaySec`(기본 10초) 지남 + 지난 확인과 크기 같음"이다(`watcher.rs:143`). (1) 받는 동안 최종 이름의 0바이트 자리표시 파일을 먼저 만들고 `.part` 에 쓰는 프로그램이 있으면, 자리표시 파일은 크기 0 으로 안정돼 먼저 옮겨진다. (2) 전체 크기를 미리 잡아 두는 프로그램(토렌트 등)이 10초 넘게 멈추면 받는 중인 파일이 옮겨진다. (3) 이벤트가 올 때마다 타이머를 1.5초 뒤로 다시 잡으므로(`watcher.rs:218-221`, `103-105`) 큰 파일을 받는 동안에는 이미 끝난 다른 파일도 기다린다.
- **고치는 방법**: (1) 크기 0 파일과, 같은 폴더에 `<이름>.part`·`<이름>.crdownload`·`<이름>.download` 가 있는 파일은 건너뛴다. (2) 안정 확인을 2회 연속으로 늘리고 대용량(예: 1GB 이상)은 대기 시간을 60초로. (3) 타이머는 "마지막 이벤트 + 1.5초"와 "첫 이벤트 + 15초" 중 이른 쪽.
- **나아지는 점**: 받는 중인 파일을 건드릴 여지가 줄고, 긴 다운로드 중에도 자동 정리가 돈다.
- **예상 결과**: `watcher.rs` 테스트 3개 추가(자리표시 파일, 형제 `.part`, 이벤트 연속).

### 🟡 7. 덮어쓰지 않기가 확인과 이동 사이에 틈이 있다

- **지금 문제**: `plan_move` 가 `dest.exists()` 를 본 뒤(`organizer.rs:323`) `fs::rename` 을 부른다(`:671`). `rename` 은 목적지가 있으면 덮어쓴다. 그 사이에 같은 이름 파일이 생기면(동기화 클라이언트, 다른 Smash 프로세스인 MCP) 덮어쓴다. 되돌리기도 같다(`:790-793`). `exists()` 는 끊어진 심볼릭 링크를 "없음"으로 본다.
- **고치는 방법**: 맥은 `renamex_np(..., RENAME_EXCL)`, 리눅스는 `renameat2(RENAME_NOREPLACE)`, 윈도우는 `MoveFileExW` 를 `MOVEFILE_REPLACE_EXISTING` 없이. `EEXIST` 면 ` (2)` 로 다시 계획한다.
- **나아지는 점**: 덮어쓰지 않는다는 약속이 OS 수준에서 보장된다.
- **예상 결과**: 테스트에서 `plan_move` 뒤에 목적지를 만들어 넣고 `move_file` 이 실패하는지 확인.

### 🟡 8. 다른 디스크로 옮길 때 속성이 빠지고 실패 흔적이 남는다

- **지금 문제**: 디스크가 다르면 `File::open` + `io::copy` 로 복사한다(`organizer.rs:673-686`). 실행 권한, 확장 속성(Finder 태그, "받은 곳", 격리 표시)이 빠진다. 복사가 중간에 실패하면 반쪽 파일이 목적지에 남는다. 원본을 지우기 전에 `sync_all` 을 하지 않는다.
- **고치는 방법**: 목적지 폴더의 임시 이름(`.smash-<id>.tmp`)으로 `fs::copy`(맥에서는 속성까지 복사)한 뒤 `sync_all`, 7번의 덮어쓰지 않는 rename 으로 제 이름을 주고, 그다음 원본을 지운다. 실패하면 임시 파일을 지운다. `.smash-*.tmp` 는 기본 건너뛰기 패턴에 넣는다.
- **나아지는 점**: 외장 디스크로 정리해도 파일이 원본과 같다.
- **예상 결과**: 디스크 간 이동 뒤 `xattr -l` 결과가 원본과 같다.

### 🟡 9. 실패한 파일을 화면에서 볼 수 없다

- **지금 문제**: 결과 토스트는 실패 수와 첫 번째 파일만 6초 보여 준다(`app.js:462-471`). 나머지는 어디에도 남지 않는다. 기록에는 성공한 `Op` 만 들어간다(`organizer.rs:749`, `758`).
- **고치는 방법**: 실패가 있으면 미리보기 위에 접을 수 있는 결과 띠("3개는 그대로 있어요")에 파일과 사유를 전부 적고, `Run` 에 `failed: [{file, reason}]` 을 더해 기록 탭에도 남긴다.
- **나아지는 점**: 무엇이 안 옮겨졌는지 찾으러 폴더를 뒤지지 않는다.
- **예상 결과**: 실패 0건이면 지금과 같고, 있으면 띠가 사라지지 않는다.

### 🟡 10. `Cargo.lock` 이 저장소에 없다

- **지금 문제**: `git ls-files` 에 `Cargo.lock` 이 없다. 릴리스 워크플로는 매번 그 시점의 최신 호환 버전으로 의존성을 푼다(`release.yml` 에 `--locked` 없음). 같은 태그를 다시 빌드해도 다른 바이너리가 나오고, 파일을 옮기는 앱에 검증 안 된 의존성 갱신이 들어갈 수 있다. `package-lock.json` 은 추적된다.
- **고치는 방법**: `src-tauri/Cargo.lock` 을 커밋하고 CI 의 `cargo test`·`tauri build` 에 `--locked`(Tauri 는 `-- --locked`)를 붙인다.
- **나아지는 점**: 테스트한 의존성과 배포한 의존성이 같다.
- **예상 결과**: 잠금 파일이 낡으면 CI 가 실패로 알려 준다.

### 🟡 11. 스캔 상한에서 조용히 잘린다

- **지금 문제**: 하위 폴더 스캔은 20,000개·깊이 8에서 멈추는데(`organizer.rs:34-35`, `410`, `435`) `Scan` 에 잘렸다는 표시가 없다. 사용자는 전부 본 줄 안다.
- **고치는 방법**: `Scan.truncated: bool` 을 더하고 미리보기 머리에 "20,000개까지만 봤어요. 정리한 뒤 다시 보기를 눌러 주세요."
- **나아지는 점**: 큰 폴더에서 "왜 남았지"가 없어진다.
- **예상 결과**: 한 줄 안내.

### ⚪ 사소

- `PROJECT_MARKERS` 의 `".sln"` 은 파일 이름 전체와 비교하므로 `Foo.sln` 을 잡지 못한다(`organizer.rs:32`, `395`). 확장자 비교로 바꾸거나 뺀다.
- `inside_any_root` 는 글자만 정리해 비교한다(`organizer.rs:211-214`, `config.rs:88-103`). 정리 대상 안의 폴더 심볼릭 링크를 목적지로 주면 링크가 가리키는 바깥으로 나간다. 규칙으로는 사용자 의도일 수 있지만 MCP 의 `moves` 에는 `canonicalize` 비교를 더하는 편이 낫다.
- 자동 정리를 켜면 1.5초 뒤 지금 쌓여 있는 파일 전부가 대상이 된다(`watcher.rs:88-89`). 미리보기 없이 실행된다(기획 2).

- 탭 이름 "자동 정리 · Claude" 안에 언어·업데이트·효과 설정이 다 있다(`app.js:1080`, `README.ko.md:87`). "설정"으로 바꾸는 편이 찾기 쉽다.
- 테스트가 전역 `SMASH_HOME` 과 잠금 하나에 묶여 `--test-threads=1` 이 필요하다(`test_util.rs:7-21`). `config_dir()` 를 인자로 넘기면 병렬로 돈다.

## 기능 기획 제안

### 1. 기록에서 골라 되돌리기 + 휴지통 복원 (크기 M)

- **무엇을**: 🟠 1·2 를 기능으로 묶은 것. 기록 탭의 실행마다 "되돌리기", 휴지통 간 파일도 함께 복원, 중단된 실행 복구.
- **왜 맞는가**: 결정기록이 되돌리기를 재미보다 앞에 뒀다. 한 대 때리고 "미안" 할 수 있어야 또 누른다.
- **흐름**: 기록 → 실행 펼침 → 되돌리기 → "24개 돌려놨어요. 2개는 원래 자리에 같은 이름이 있어 남겼어요 [보기]".
- **범위**: `organizer.rs`(`undo_run`, 실행별 파일), `trash.rs`(결과 경로 반환), `app.js` 기록 줄, MCP `undo_last` 에 `run_id` 선택 인자.

### 2. 자동 정리 첫 켤 때 한 번 보여 주기 (크기 S)

- **무엇을**: 자동 정리를 켜면 바로 실행하지 않고 "지금 쌓인 37개를 이렇게 치울게요" 미리보기를 한 번 띄운다. 휴지통 규칙을 자동 정리에서 뺄지 고르는 체크도 여기 둔다.
- **왜 맞는가**: 엄마도 처음엔 말로 한다. 지금은 켜는 순간 말없이 때린다(`watcher.rs:88-89`).
- **범위**: `app.js` 자동 정리 토글, `Target.auto_trash: bool`, `watcher.rs:121` 에서 필터.

### 3. 잔소리 단계 (크기 S~M)

- **무엇을**: 자동 정리를 안 켠 폴더에 규칙에 걸리는 파일이 쌓이면 단계별로 잔소리한다. 20개 "방 좀 치워라", 60개 "으이구, 발 디딜 틈이 없네", 150개 "셋 센다. 하나…". 트레이 아이콘의 손이 단계마다 조금씩 올라간다. 배너를 누르면 미리보기가 열린다.
- **왜 맞는가**: 지금 잔소리 배너는 이미 치운 뒤에만 나온다(`lib.rs:505-523`). 등짝 스매시 전에는 원래 잔소리가 있다.
- **흐름**: 10분 주기 스윕(`watcher.rs:17`)이 켜지 않은 폴더는 세기만 한다 → 단계가 오르면 배너 한 번 → 하루 한 번 이상 안 뜸, 설정에서 끔.
- **범위**: `watcher.rs` 에 세기 전용 경로, `lib.rs` `show_nag` 재사용, 트레이 아이콘 3종(`assets/`).

### 4. 받은 날짜 조건과 "어디서 왔나" 조건 (크기 S~M)

- **무엇을**: 🟠 5 의 추가된 시각을 규칙 조건으로 드러내고("받은 지 N일"), 맥의 `com.apple.metadata:kMDItemWhereFroms` 로 "받은 곳" 조건을 더한다(예: 주소에 `github.com` 이 들면 `개발리소스`).
- **왜 맞는가**: 다운로드 폴더의 파일은 이름보다 출처가 분류를 더 잘 말해 준다. 파일 내용은 여전히 읽지 않는다.
- **범위**: `FileInfo` 에 `added_ms`·`from`, `Match` 에 `from_includes`, 규칙 편집기 한 줄. 윈도우는 `Zone.Identifier` 대체 스트림.

### 5. MCP 는 보여 준 계획만 실행 (크기 S)

- **무엇을**: `apply_plan` 의 자유 `moves` 를 `plan_moves`(검증 + 계획 id 발급)와 `apply_plan(item_ids)` 둘로 나눈다. 서버는 자기가 돌려준 id 만 실행한다.
- **왜 맞는가**: 지금 "사용자에게 보여 주고 동의받을 것"은 도구 설명의 부탁일 뿐이다(`mcp.rs:30`). 미리보기 → 실행이라는 앱의 순서를 MCP 에서도 구조로 지킨다.
- **범위**: `mcp.rs` 도구 하나 추가, `last_plan` 재사용. 테스트 1개.

### 6. 규칙이 왜 이 파일을 잡았나 (크기 M)

- **무엇을**: 미리보기 항목을 누르면 "규칙 '계약서'가 먼저 잡음(이름에 '계약서'). 그다음 '문서'도 맞지만 순서가 뒤" 를 보여 주고, 그 자리에서 규칙 순서를 바꾼다.
- **왜 맞는가**: 규칙이 늘면 우선순위가 유일한 혼란 지점이다. 지금은 `reason` 에 규칙 이름만 담긴다(`organizer.rs:550`).
- **범위**: `scan_target` 에서 맞는 규칙 전부를 모아 `Item.also_matched`, `app.js` 항목 펼침.

### 7. 주간 성적표 (크기 S)

- **무엇을**: 일요일 저녁 배너 한 번. "이번 주 142개 치움, 휴지통 1.2GB. 다운로드에 아직 31개." 기록 탭 위에도 같은 줄.
- **왜 맞는가**: 잔소리만 하는 엄마는 없다. 치운 만큼은 알아준다.
- **범위**: 실행별 기록 집계(기획 1 이후), `show_nag` 재사용.

## 디자인·인터랙션 제안

비평 기준은 impeccable 스킬의 critique 항목을 참고했다. 화면 판단은 `src/renderer` 의 HTML·CSS 와 README 이미지에 근거한다(앱은 띄우지 않았다).

먼저 지금 잘 된 것. 본 화면은 "무채색 장부"로 정해 두고 빨강을 새 폴더·휴지통에만 쓴다(`style.css:1-6`). 그림자·그라데이션이 없고 색 토큰이 한 벌이다. 흔한 생성 티(보라 그라데이션, 유리 카드, 이모지 아이콘)는 없다. `prefers-reduced-motion` 도 처리했다(`smash.css:86-90`). 고칠 곳은 컨셉이 효과 창 안에만 갇혀 있다는 점이다.

1. **소리가 없다.** 저장소에 오디오 파일도 재생 코드도 없다. 등짝 스매시의 절반은 소리다. 타격 순간(0.8초, `lib.rs:43`)에 맞춰 짧은 "찰싹"(150ms 안팎) 하나를 `smash.html` 에서 재생한다. 볼륨은 시스템 알림음 수준, 설정의 효과 스위치 옆에 "소리" 스위치를 따로 둔다. 자동 정리 배너는 소리 없이 둔다.
2. **한 개를 옮겨도 화면 전체가 흔들린다.** 효과는 파일 수와 무관하게 2초 고정이고(`lib.rs:42`) 창 흔들림도 고정값이다(`lib.rs:364`). 세기를 셋으로 나눈다: 1~5개는 손가락으로 "톡"(0.6초, 흔들림 없음), 6~50개는 지금의 "찰싹!!", 그 이상은 흔들림 폭 1.5배에 글자 "철썩!!!". `smash.html?lang=…&n=…` 로 수를 넘기면 CSS 클래스 하나로 갈린다.
3. **때린 결과가 화면에서 이어지지 않는다.** 손이 내려온 뒤 미리보기는 `doScan()` 으로 통째로 바뀐다(`app.js:476`). 타격 순간에 `main` 창으로 이벤트를 보내, 체크된 행들이 위에서부터 30ms 간격으로 납작해지며(높이 0, 150ms) 빠지게 한다. 맞아서 정리됐다는 인과가 보인다.
4. **긴 정리에서는 손이 먼저 퇴장한다.** 효과 창은 타이머로 닫히고(`lib.rs:347-351`) 실제 이동은 그 뒤에도 계속될 수 있다. 버튼에는 "정리 중…" 스피너만 남는다(`app.js:461`). 1.5초를 넘기면 손이 누른 자세로 멈춰 있고 오른쪽 아래에 "312 / 1,480" 을 센다. 끝나면 들어 올린다.
5. **헛스윙이 없다.** 전부 실패해도 같은 "찰싹!!" 이 나온 뒤 실패 토스트가 뜬다. 효과는 결과를 모르고 시작하므로, 결과가 0건이면 닫히기 전에 글자를 "어라?"로 바꾸는 꼬리 장면 하나를 둔다.
6. **잔소리 배너가 한 문장뿐이고 멈출 수 없다.** 제목이 항상 "으이구!! 폴더 청소 좀 하랬지!!"다(`nag.html:14`). 4.5초 뒤 타이머로 창이 사라져(`lib.rs:496-499`) 읽다가 놓친다. 문구를 대여섯 개로 늘리고 파일 수에 따라 고른다("이게 다 뭐니", "엄마가 또 치웠다"). 마우스를 올리면 타이머를 멈춘다.
7. **빨강의 약속이 한 곳에서 깨진다.** 빨강은 "봐야 할 곳"인데 주 버튼 `짝! 정리하기`는 먹색(`--primary`)이고 클래스만 `smash` 다(`index.html:35`). 지금 규칙을 지키려면 그대로 두고, 대신 눌렀을 때 버튼이 2px 눌리며 0.1초 빨갛게 번쩍이는 것으로 타격의 시작을 알린다.
8. **되돌리기에 컨셉이 없다.** "마지막 작업 되돌리기"(`index.html:62`)와 토스트 "원래 자리로 돌려놨어요"는 평범하다. 되돌릴 때는 손이 아니라 쓰다듬는 짧은 모션(손바닥이 가볍게 두 번 내려앉음, 0.5초)과 "미안, 없던 일로" 한 줄. 스매시와 짝이 되는 유일한 반대 동작이다.
9. **규칙 밖 파일 영역이 조용하다.** "규칙 밖 12개"는 숫자로만 나온다(`app.js:327`). 이 앱에서 가장 Claude 를 쓰게 되는 자리다. "얘네는 어디 둘지 모르겠다" 한 줄과 함께 Claude 버튼을 그 문장 바로 옆에 둔다.

## 성능 제안

- **휴지통이 파일마다 프로세스를 띄운다**(`trash.rs:17-21`, 윈도우 `:34-39`). 맥은 회당 최소 36ms(측정), 윈도우 PowerShell 은 더 느릴 것으로 보이나 재지 못했다. 한 실행의 휴지통 대상을 모아 `osascript` 한 번에 인자로 넘기면 1,000개가 36초 이상에서 1초 안쪽으로 준다. 결과 URL 을 받는 수정(🟠 2)과 같이 한다.
- **`decorate` 가 항목마다 `missing_dirs` 로 폴더 존재를 확인한다**(`lib.rs:111-116`, `organizer.rs:603-614`). 20,000개면 `exists()` 가 수만 번이다. 폴더 경로로 묶어 한 번씩만 본다.
- **미리보기가 한 번에 전부 그린다**(`app.js:339` 의 `innerHTML`). 상한인 20,000개면 DOM 노드가 수십만 개가 된다. 폴더 노드는 접힌 채로 그리고 펼칠 때 자식 행을 만든다. 측정은 못 했다.
- **큰 중복 파일을 네 번 읽는다.** 스캔에서 두 파일 해시(`organizer.rs:324`), 실행에서 다시(`:723`). 스캔 때 구한 해시를 `Item` 에 담고 실행에서는 크기·수정 시각이 같으면 재사용한다.
- **감시 이벤트마다 최상위 폴더를 다시 훑는다**(`watcher.rs:121`). 다운로드 폴더 크기에서는 문제 될 수준이 아니다. 바꿀 필요 없다.

## 확인 못 한 것

- 앱을 띄워 보지 않았다. 효과·배너·화면 배치는 코드와 README 이미지로만 판단했다.
- 윈도우에서는 아무것도 돌리지 못했다. 휴지통 PowerShell 호출의 속도와 오류 대화상자 여부, NSIS 설치·자동 업데이트, 경로 처리 전부 확인 못 함. README 도 실제 기기 미검증이라고 적고 있다.
- 서명·공증·자동 업데이트의 실제 동작(릴리스 자산, `latest.json` 서명, 초안 → 공개 절차)은 워크플로 파일만 읽었다. 릴리스 페이지는 조회하지 않았다.
- `trash_keeps_original` 테스트와 감시 테스트의 휴지통 단정은 로컬 맥에서 건너뛰게 돼 있다(`organizer.rs:1015-1017`, `watcher.rs:307`). 29개 통과에 실제 휴지통 이동은 들어 있지 않다.
- 🟡 6 의 (1)·(2)는 코드의 판정식에서 나온 결론이다. 어느 브라우저·프로그램이 실제로 그렇게 쓰는지는 실행해 확인하지 않았다. 🟠 5 도 브라우저별 수정 시각 처리(서버의 Last-Modified 를 쓰는지)는 확인 못 함.
- 🟠 1·3 의 중단·경합은 재현 테스트를 만들지 않았다(저장소 안에 테스트 파일을 추가해야 해서). 코드 경로로만 확인했다.
- `claude.rs` 는 CLI 인자(`--tools ""`, `--strict-mcp-config`)와 MCP 등록 부분만 읽었다. 프롬프트 본문, 응답 해석, 사진 묶기 흐름은 훑어보기만 했다. `thumbs.rs` 와 `grouping.rs` 뒷부분, `app.js` 의 규칙 편집기·설정 화면 대부분, `docs/설계서.md`·`구현도.md` 본문도 읽지 않았다.
- 결정이 필요한 것: (1) 휴지통 규칙을 자동 정리에서 기본으로 뺄지. (2) 소리를 기본 켬으로 할지. (3) 기록을 실행별 파일로 바꿀 때 기존 `history.json` 을 옮길지 그대로 둘지.
